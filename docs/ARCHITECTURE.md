# Architecture and data behavior

Native SwiftUI app and WidgetKit extension targeting iOS 26 and later. No backend, login, external runtime package, analytics or remote habit storage. `Package.swift` compiles the same Foundation-only core files separately for tests. The Xcode targets compile these shared files directly, so runtime writes and tests use the same implementation.

## Storage

`habits-v1.json` in the App Group contains a versioned Codable snapshot. Every write opens an advisory process lock, reloads the latest snapshot, applies the mutation, validates all invariants, and atomically replaces the file. Independent repository instances are tested with 30 concurrent increments. Failed validation leaves the committed file unchanged. This JSON repository was selected over the earlier research proposal's SwiftData adapter to share one transactional write path with widget processes and to test recovery on Linux.

The store and its daily snapshots are written as compact JSON; portable exports stay formatted unless formatting would push them past the 64 MiB import limit. A commit whose encoded size exceeds that limit is refused before the file is touched, so the app can never save a file a later launch would reject, and imports and backups are size-checked before they are read. Validation finds each record's habit through an ID index and checks keys and note lengths without building strings per record.

In the app, `AppStore.change` applies a change to the snapshot on screen (validated there, so editors still keep their draft when a save is invalid), then queues the same change on a serial persistence queue, which runs it again inside a repository transaction against the latest file. Nothing on the main thread waits for the file lock, reads, decoding, backups, encoding or the atomic write. Changes still being saved are applied again over each newly saved snapshot; one that fails is dropped and reported, and the screen takes the saved snapshot once the queue drains. A change therefore captures values rather than view state and decides from the snapshot it is given: a yes/no tap toggles the latest saved amount. Check-ins go through `AppStore.log`, which skips the full check of every record on the main thread because the shared engine checks each value it writes; the save on the queue still validates everything. Launch, foreground reloads, export, the backup list and restore run on the same queue; launch shows the empty canvas until the first read finishes, never onboarding or an empty list. Leaving the app requests background time to finish queued saves.

Up to seven dated snapshots are retained, captured before the first write on each used day. Up to three before-restore snapshots are also retained. Import is replace-only: decode and validate first, confirm in UI, preserve the original bytes, then atomically commit. A corrupt primary file can be explicitly recovered from a valid export. Unknown schema versions are rejected; migrations must be added before increasing the schema. Portable exports include settings as well as habits and records.

App Group identifiers are configured in `Config/Signing.xcconfig` and expanded into both targets' Info.plist and entitlements. The app's private-storage fallback supports simulator/development configurations lacking the group. Widget actions require shared storage rather than silently writing into an unrelated extension file. Changing the group requires exporting/importing data.

## Dates and precision

Civil `YYYY-MM-DD` keys are created in the current local time zone and never recomputed from timestamps. UTC Gregorian arithmetic operates on those civil keys, avoiding DST day-length assumptions. Counts are whole numbers. Measured totals store integer thousandths, with a nonnegative maximum of one billion units. Timestamps use whole seconds; the completion's local hour is saved independently for the time chart. Backfilled completions record the time they were entered.

Goal versions are ordered by effective date. Edits start today; repeated edits today replace today's version. Build/quit and tracking changes preserve old rule versions and reset today's amount while preserving its note. Amount editing in a previous mode is locked; note editing remains available. A restored archive records paused dates, so quit histories don't gain clean days during the archived interval.

## Scoring

Build success: amount >= historical target. Quit success: amount < historical threshold, with unlogged clean days derived only within tracked periods. Yes/no thresholds are one. Over-goal totals remain stored and qualify once. Complete is idempotent; clear preserves the note. Future, paused and archived writes are rejected, as are dates before 1970-01-01.

Any earlier past day can be backfilled, matching HabitKit's documented calendar backfill. Recording a day before a habit's start moves `created` and the first goal version's `from` back to that day, so every record still falls inside the tracked range and later goal versions keep their dates. Unlogged days in the extended range then score normally: build days count as missed, quit days as clean. A build write that leaves the day empty (amount 0, no note) changes nothing, so an accidental save cannot add missed days; saving a quit day with no slip deliberately moves the start back. Pre-start days use the first goal version, so after a build/quit conversion their amounts are locked like other earlier-mode days. The detail calendar can navigate to any month back to January 1970; its scrolling history still begins at the start month.

Daily unfinished today doesn't break yesterday's streak; a missed past day does. New habits default to Daily. None disables streak tracking while selected. At the owner's request on 18 October 2026, enabling Daily includes the preceding no-goal history in the daily run, using each date's original mode and completion target. This is calculated on read, so already-enabled habits recover too; no records, effective dates or stored goal versions are rewritten. Adjacent Daily/None versions can join once Daily is enabled, but another cadence or a build/quit mode change remains a boundary. Existing habits still set to None stay off, including after import. Weekly/monthly streaks count successful dates, not successful periods. Completed periods must meet their target; an unfinished period carries the previous streak while its target remains reachable. A period's target is capped to its tracked segment length, including short months and a partial first period. Goal versions split cadence periods at the effective day; other changes to cadence or mode start a new streak segment. These boundary choices are explicit where the reference docs don't define exact behavior.

Streak tiles, the streak list, the dashboard and the matching home-screen widgets show `Engine.streak`. For weekly and monthly build goals it counts consecutive successful periods (weeks or months) instead of dates. The current period adds one once its target is met and keeps the streak while still reachable. The same segment rules apply: a cadence or mode change starts over, and a partial first period needs only its tracked days. Other habits show the day streak from `stats`. Year views use `Engine.yearStats`: successful days, tracked days so far (today only once completed) and the longest run of consecutive successful days within that calendar year.

Streak freezes are off by default (`settings.freezesPerMonth` is 0). When the owner allows one to three a month, a missed past day of a daily build goal can be frozen from the day editor; the record stores `frozen: true`. A frozen day neither adds to nor breaks the daily streak, including the year views' longest run, and it still counts as missed in completion rates. Logging the day as done clears its freeze. Each habit has its own monthly allowance; lowering the allowance keeps freezes already used. Weekly, monthly, no-goal and quit habits can't be frozen, and validation rejects a freeze on today, a future day, a non-daily goal or a successful day.

Completion rate counts eligible build dates through yesterday plus today if completed. Quit dates and archived pauses are excluded. Aggregate current/best streak is the maximum across selected habits; it is not a combined all-habits streak. Monthly/year totals count distinct successful habit-days. Time-of-day counts saved completion hours for qualifying build dates.

## Month page layouts

The Month bottom-bar page's independent `settings.calendarLayout` is an optional `CalendarLayout` (`grid`, `month`, `year`). Nil means the existing compact grid and is omitted when encoded; older schema-one snapshots therefore retain their layout. The choice goes through `AppStore.change`, shares the existing transactional persistence/export path and does not alter habit records or the main `settings.layout` page. It is an app-only setting, so it triggers neither widget nor reminder reloads. Month/year cards receive the visible data, habit version and selected period, and reuse `CalendarDay`, `MonthDots` and `Engine.yearStats`; day editing uses `DayEditorView` and the shared engine. Period selection is view state rather than a reinterpretation of saved civil dates.

## Hidden habits

`Habit.hidden` (optional, written only when true) marks an active habit hidden, for showing the app to someone. Hiding changes only what is shown. `BuddyData.withoutHidden` is the data as screens and widgets see it: hidden habits are left out, as is any routine whose active habits are all hidden; hidden memberships are removed from visible challenges, and a challenge with no visible members is omitted. Their days stay in `records`, where nothing finds them without their habit; copying the records instead cost each check-in about 8 ms on a 67,000-record store. Code that walks every record must skip habits not in `habits`, as Explore's note count does. Other routines and dashboard widgets keep their IDs, which simply find no habit, so a dashboard widget for a hidden habit is hidden like one for an archived habit. `AppStore.visible` caches that copy once per published snapshot; lists, summaries and background work (Explore, Insights, Statistics, Notes, the recap and the calendar) read it, and every change still runs through `change` against the full data. Widget entries filter it when they are created; a widget whose chosen habit or routine is hidden says so instead of showing it. Writes, reminders, Shortcuts, Control Center controls, timers, exports and backups use the full data, so a hidden habit still logs, keeps its reminders and is completed by its routines. `BuddyData.reorder(_:)` orders the habits shown and leaves hidden habits in their places. The Hide Habits list, opened from Compact List Settings or Settings, lists every active habit.

## Theme and accent

`settings.accent` (optional, written only when set) holds the app accent: a palette name such as `teal` or a custom color as `#RRGGBB`. Nil is the reference violet, so older files and new installs are unchanged. `AccentCode` (Foundation only, unit tested) parses and formats the custom form, and validation accepts only those two forms. The app resolves it once at the root into the `accent` environment value (`Accent`: the color, and white or 75% black for text and glyphs on it, by relative luminance) and sets it as the SwiftUI tint and the window tint. An unknown name falls back to violet. Views read the environment. Views rendered to images (the weekly recap poster) and widgets read `data.settings.accent` instead, because an image renderer or widget has no app environment. `DashboardWidget.tint` falls back to the accent for multi-habit designs. An accent change reloads widgets (`SyncScope`), since home-screen multi-habit widgets use it; it doesn't touch reminders.

`Theme.colorScheme` maps the theme to the root `preferredColorScheme`. The Settings sheet also takes the overview's effective scheme: a presented sheet otherwise keeps the scheme it opened with, and keeps a light or dark one after System is chosen.

`settings.glass` (`GlassSettings`, optional, not written until first set) holds the Liquid Glass switch, transparency (0 Clear, nil System, 1 Frosted), tint (`accent`, a palette name or `#RRGGBB`) and tint strength. Turning the switch off keeps the rest. Validation checks the ranges and the tint's form.

The root resolves it with the accent into the `glass` environment value (`GlassStyle`, nil when off). Views read it through these helpers:
- **`glassChrome(in:prominent:fill:border:)`**: the flat fill and hairline when off. When on, the control color at the chosen strength, then an interactive `glassEffect`. Prominent controls take regular glass tinted with the accent.
- **`GlassGroup`**: wraps neighbouring controls in a `GlassEffectContainer`, in glass mode only.
- **`topBar`**: puts a screen's top controls in a `safeAreaBar`. It hides the scroll edge effect, and draws the canvas backdrop that flat bars had, unless glass is on.
- **`buddySheet(partial:)`**: in glass mode, leaves a half-height sheet's background to iOS.

Widgets, reminders and exports don't read the glass settings, so a change doesn't reload widgets.

## Routines, timers and analysis

`BuddyData.routines` holds named groups of habits (name, icon, color, ordered habit IDs). Older schema-1 files decode with no routines. Validation requires unique IDs, a name, no repeated habit and only existing habit IDs; deleting a habit permanently goes through `Engine.deleteHabit`, which also removes it from routines. `Engine.completeRoutine` completes every open build habit in the routine on one day through `Engine.complete` (so a count fills to its target and an over-goal total is kept); quit habits and already successful habits are left alone. The app, the Complete Routine Shortcut and the Control Center control all use it.

`BuddyData.challenges` stores at most 100 named 7-, 14- or 30-day challenges, each with a start day and up to 20 unique existing habit IDs. Older schema-1 files decode with no challenges. Challenge progress is derived from the ordinary habit records by `ChallengeProgress`: a day counts only when every selected habit succeeds, and existing check-ins within the challenge dates count. Explore hides hidden habit memberships and removes challenges with no visible habits from its snapshot; editing preserves hidden memberships, while permanently deleting a habit removes that membership and deletes a challenge if no members remain. The challenge detail uses the existing day editor for logging and backfilling, so challenges introduce no second check-in store.

A habit takes a timer when its current goal is a build goal tracked yes/no, or counted or measured in seconds, minutes or hours (`s`, `sec`, `min`, `minutes`, `h`, `hours` and similar). Finishing logs the elapsed time to the day the timer started, capped at a countdown's length: measures keep thousandths of the unit, counts keep whole units, yes/no goals complete. Other units, quit habits and zero-length count sessions log nothing. The running session lives in App Group defaults; the in-app timer and the Live Activity's Finish and Cancel buttons (`LiveActivityIntent`, run in the app process) read the same session and write through the shared repository and engine. A countdown schedules one local notification (`timer.end`), outside the `buddy.` reminder namespace that reconciliation replaces. Finishing goes through `TimerSessions.finish`, which claims the running session inside the store's locked transaction, so the in-app Finish and the Live Activity's can't both log it; if the save fails the session is restored. `TimerSessions.stop` runs off the main thread but posts its change notification on it, since the overview reloads the store when it hears it (it used to, from a background thread, and SwiftUI warned "Publishing changes from background threads").

`InsightsSummary`, `WeekRecap` and `Milestones` are read-only and unit tested. Insights treat a kept day as a build success or a clean quit day, over tracked days (past days, and today once kept or slipped), so build and quit habits share one scale; this differs deliberately from Statistics, which counts build days only. Weekday rates and time of day cover the chosen range; the monthly trend always covers the last twelve months. "Slip together" compares each pair of habits on the past days both were tracked: days both lapsed over days either lapsed (at least three together and 40%), strongest three shown, among the first 30 habits. The weekly recap uses the same kept-day rule for the chosen week and the one before, plus perfect days (every tracked habit kept), the day with the most kept habits and the number of notes. Milestones are streak badges at 3, 7, 14, 30, 50, 100, 180 and 365 days (from the best day streak, as on the detail screen) and total badges at 1, 10, 25, 50, 100, 250, 500 and 1,000 successful days, with the day each total was reached.

## Notifications and automation

One-off local notifications cover a rolling seven-day window, with 60 earliest requests reserved below the system's pending-request limit. The UI reports omitted requests. Launch, logging and settings changes refresh the schedule. All scheduling in a process goes through `ReminderCoordinator`, which runs one reconciliation at a time and collapses requests that arrive meanwhile into one run with the newest data; each run removes only `buddy.` requests whose content or time changed and adds the missing ones. Today is suppressed after build success or quit failure. Settings permission denial preserves reminders and offers a system-settings link. Travel and DST are handled using local calendar components; continuous background rescheduling while the app is never opened is not guaranteed.

`settings.dashboard` stores the dashboard: an ordered list of widgets, each with a design, a style (auto, light, dark, tinted) and optional fields added within schema 1 and decoded with defaults: `size` (small, medium or large; nil or a size the design lacks uses its default), `habitID` for single-habit designs, `habitIDs` for multi-habit designs (nil shows every active habit, in habit order), `routineID`, a `title` for multi-habit designs and a palette `color` in place of the habit's or routine's. Unset fields are not written. Thirteen designs: streak, goal ring, next badge (small); stats, routine, today ring (small or medium); this month (small or large); 20 weeks, three months, this week (medium); this year (medium or large); today list (medium or large); quick check (small, medium or large). While the list is nil the app shows `DashboardWidget.defaults` with stable IDs; the first edit stores the arrangement, so later habit changes don't reshuffle it. Widgets whose habit (or every chosen habit) is archived or deleted, or whose routine was deleted, are hidden rather than removed (`DashboardWidget.visible`). Validation caps the list at 100 entries with unique IDs, unique chosen habits, titles of at most 100 characters and colors of at most 40; portable exports include it. `DayRate(habit, days:)` gives the kept share of recent days and `WeekRates` each day of a week across chosen habits, both on the same tracked-day rules as Insights.

The dashboard views live in `Shared/UI/HabitWidgets.swift` and `MoreHabitWidgets.swift` and are drawn by both the in-app dashboard and matching WidgetKit widgets in the same sizes (Streak, This Month, 20 Weeks, Three Months, Today List, Today Ring, Goal Ring, Habit Stats, This Year, Next Badge, Quick Check, This Week and Routine); `DashboardHomeWidget` maps the widget family to the design's size. In the app the check runs the shared `AppStore` logging path and Complete All runs `Engine.completeRoutine`; on the home screen they run `WidgetLogIntent` (or open the app when a numeric total needs editing) and `CompleteRoutineIntent`. Home-screen widgets choose a habit, habits or routine (`ChooseRoutineWidgetIntent`) and a theme; titles and colors are dashboard-only, so home-screen widgets keep each habit's color. Widget themes gained Tinted.

The widget extension also has a small Today Ring widget (one colored segment per habit, filled when done) that reads well in StandBy, where widgets lose their background and light styles switch to dark; Lock Screen widgets for a habit's streak (a ring that fills when today is done) and for today's count; Control Center controls to log a habit, complete a routine and open the timer (the same controls can be assigned to the Action button); and the timer's Live Activity with Dynamic Island layouts. Controls reload with widgets after writes that change habits, records, routines or a setting widgets show (week start, notes, accent); app-only settings such as the theme, layout, card options and dashboard reload neither widgets nor reminders. A write that names the habits it edits (a check-in in the app, the Shortcut, widget and control intents, a timer) reloads only the widget kinds with an installed widget that can show one of them: `AppEnvironment` reads each installed widget's configuration intent (`WidgetCenter.currentConfigurations()`), and `WidgetTargets` (Foundation only, unit tested) picks the kinds. A widget left on its default habit, routine or every habit counts as showing any habit, and WidgetKit reloads a kind as a whole. Those writes reload the Log Habit and Complete Routine controls, never the Habit Timer control, which doesn't change. Adding, removing or reordering habits, routine and setting changes, restores and anything else reload every widget and control. `settings.recapReminder` adds one notification at 7 PM on the last day of each week.

Widgets request periodic/midnight refreshes and use the same repository and engine for writes. All eight Shortcut actions (including Complete Routine) are defined in `HabitIntents.swift`; their phrase provider lives in the app-only `HabitShortcuts.swift` to avoid training duplicate extension phrases. Get Progress returns JSON with exact amount strings, goal, remaining, unit, note and success. Numeric totals needing an editor should open the app; no keyboard runs inside a widget. Widgets and Siri execution still need real iPhone validation. Retrying a non-idempotent increment as a separate invocation intentionally adds another increment.

## Icon suggestions

`IconSuggester` (Foundation only, unit tested) ranks icons for a habit name. `IconCatalog.entries` holds 252 concepts and about 2,400 terms, each a line of Lucide icon names (`!name` marks the crossed-out variant, `*0.8` scales the concept) and comma-separated terms (phrases allowed, `~` marks a weak term). Matching folds case and accents, drops bare numbers and filler words, and stems lightly (plurals, -ing, -ed, -ation, final e, y to i, doubled consonant) so word forms meet. Phrases match first and claim their words. Single words then score: exact stem, else a prefix match for the word still being typed (four letters or more), else a typo within one edit (five to seven letters) or two (eight or more) against the same first letter. Later words get up to 0.15 more, so the object outranks the verb ("Walk the dog"); words after a preposition that follows a recognized word count 70% with no bonus ("Gym after work"). A negation word or a quit habit raises concepts that have a crossed-out icon by 25% and leads with that icon; otherwise a ban icon follows the habit's icon. Alternative icons follow at 60% and less. Only when no catalog word matches does it fall back to the bundled Lucide names (0.5) and keywords (0.25), ignoring words shared by more than 20 icons. Catalog icons missing from the bundle are dropped; a test checks every catalog icon exists in `lucide-icons.json`. The app builds one instance from the bundled index, warmed off the main thread at launch (about 30 ms optimized); a suggestion takes microseconds. The editor recomputes once typing pauses for 250 ms (`.task(id:)` on the name), and immediately on save or a build/quit change.

## Project maintenance

`scripts/generate-project.py` deterministically emits the checked-in app/widget project and shared scheme. It has no external dependency. `check-project.py` checks source membership, plist validity, research hashes and gallery links. Research folders are not app resources. UI styling lives in shared tokens rather than copied screenshot raster assets.

## Visual audit fixtures

Debug-only launch environment options select an isolated `VisualAudit` repository, deterministic synthetic habits and a civil date. `BUDDY_VISUAL_SCREEN`, `BUDDY_VISUAL_DATE`, `BUDDY_VISUAL_THEME`, `BUDDY_VISUAL_ACCENT` (a palette name or `#RRGGBB`) and `BUDDY_VISUAL_GLASS` (`on`, or `transparency:tint:strength`) drive native UI capture, and the `theme` screen opens Settings on the Theme page; `BUDDY_VISUAL_RESET=false` verifies relaunch persistence. `BUDDY_VISUAL_FIXTURE=reference` loads the two habits from the owner's comparison screenshots into its own `VisualAudit-reference` store, so its October dates cannot invalidate the August-dated test store. `BUDDY_VISUAL_HABIT` picks which habit a detail or editor screen opens. The fixture writes never touch the normal App Group/private habit repository. No private user data is captured or printed. UI test attachments retain PNG screenshots; JPEG chunks in CI logs allow reference review without an artifact download.

Overview visibility fields decode with defaults so schema-one backups from before the new options remain readable. New installs start with the dark theme and plain overview cards (no month/weekday labels, streak or goal chips). Decoding keeps the earlier fallbacks (System theme, everything shown) for keys missing from older backups, so restored data looks as it did. A habit can override its seven card appearance fields; reverting to defaults clears the optional override. Font Awesome Free 7.0.0, Lucide 1.51.0 (`lucide-static`, ISC) and five Figtree weights (SIL OFL) are included in both app and widget resource bundles with their licenses; `scripts/import-ui-assets.py` regenerates `Lucide.ttf`, `lucide-icons.json` and the Figtree files from the upstream packages. Fonts are registered for the process at app and widget launch. Habit symbols keep their `fa:` or `lu:` prefix, so existing icons are never reinterpreted. Third-party app screenshots remain outside both bundles.

Statistics derives monthly/hourly totals once per selected habit/year/data change. It no longer recalculates those totals inside each chart mark. `Day` stores an integer day count beside its `YYYY-MM-DD` key; parsing, `adding`, `distance`, `weekday`, month ends and comparison use integer proleptic Gregorian arithmetic for years 1583–9999, so grids, streaks and JSON decoding never construct a Calendar or DateFormatter per day. Foundation's Gregorian calendar is Julian before the 1582 reform, so earlier dates fall back to the single private immutable UTC/POSIX DateFormatter and keep Foundation's exact rules. `testFastCivilArithmeticMatchesFoundation` checks every day from 1900 through 2099 against Foundation. Display formatters (`Day.shortMonth`, `monthYear`, `longDay`) are created once and shared.

Each `BuddyRepository` caches its last read or committed snapshot keyed by the exact file bytes and validation day. Every load and transaction still takes the lock and re-reads the file; decoding is skipped only when the bytes are identical, so widget and Shortcut writes are always seen. Each process keeps one repository (`AppEnvironment.repository`), so widget timelines, controls and entity queries reuse its decoded snapshot. The app coalesces widget reloads and notification rescheduling after a burst of saves (350 ms, serialized, flushed when the app moves to the background).

`Engine.history` reads a habit's days once and shares them between the completion rate, the streak rules and the milestone totals. The store keeps a `HabitSummaries` cache of each habit's history and streak and passes it to views through the environment, so cards, the dashboard, the streak list and Milestones compute a habit again only when it changes; widgets compute directly. When the overview opens on streaks (the streak and list layouts, or cards with streak chips), the first read from disk also works out every active habit's summary on the persistence queue, so launch draws them without reading histories on the main thread. Otherwise the habits show first, and a low-priority task then fills the cache for the screens opened next; its results are dropped if a newer snapshot came out meanwhile. After a change to several habits, a new day, or a change that may touch every habit (settings, a restore, a write from a widget or Shortcut), the habits' previous results stay on screen while a background task works out new ones from that snapshot; when they arrive the store moves those habits' versions and their views redraw. A newer snapshot meanwhile starts the work again from it. A check-in on one habit instead drops that habit's result and works it out when the card next draws: ten habits with ten years of daily days take about 7 ms on this Mac (`testMeasureTenYearHistories`, release build), so about a millisecond for one, less than drawing its card twice.

Each change names the habits whose days it edits (`log(_:)`, `change(touching:)`); habits whose definition changed are found by comparing the two snapshots, which share storage for everything a change left alone. `AppStore.version(_:)` counts these per habit and moves for every habit when a change can't say what it touched, when settings, categories or routines change, or when the file held writes from a widget, Shortcut or Live Activity (the persistence queue notices because the repository no longer hands back the snapshot it last saved). Cards, compact rows, streak rows, month cards and dashboard designs are `Equatable` on that version, the habit, its options and today's date, so a check-in redraws only the habits it changed. On the iOS 27 simulator a tap went from 8–12 card bodies to 2, and from 50 compact day tiles to 5. Views keep the data as `@ViewData var data: BuddyData`. SwiftUI compares each view it rebuilds with the one before, using `==` for a property that has it, and `BuddyData`'s `==` reads every record once a change has copied them; with thirty five-year habits that comparison, repeated for every card the overview rebuilt, was three quarters of a check-in's main-thread time. `ViewData` compares with `BuddyData.isSameSnapshot`, which asks whether the records are the same storage and compares the habits, categories, routines and settings, so any new snapshot counts as changed and the `Equatable` views above decide what redraws. `AppStore.data` notifies its observers itself for the same reason: Observation's setter compares the old and new snapshots. A change still copies the records once (copy-on-write), about 2–3 ms on the simulator for 40,000 days; keeping each habit's days separately would avoid that. `AppStore` uses Observation (`@Observable`), so a view redraws only when a property it read changes. `settings` is its own property, replaced only when the settings change: the root (accent, glass, theme) and screens that read only settings don't redraw for a check-in, while a view that reads `data` still redraws for every change and relies on the `Equatable` habit views below it. Bookkeeping that views never read is `@ObservationIgnored`. Each published snapshot increases `AppStore.revision`, and Explore, Statistics, Insights, Notes and Year Review key their background work on it (with the range, habit, year or search) instead of comparing whole snapshots. That work runs off the main thread, a newer request cancels the older one, and a cancelled result is never shown. Insights work out the habits that slip together only among the first 30 habits, once per range and snapshot, and reuse them while switching between habits. The notes timeline builds a sorted index when the data changes and filters it 120 ms after typing pauses.

The scrolling contribution history is split into 16-week chunks in a lazy stack, so only chunks near the visible part are created and drawn, however far back a habit goes; the oldest chunk can start up to 15 weeks before the history in the faint pre-start shade. Compact rows, notes, milestones, routines and the day and routine sheets scroll lazily. The dashboard stays eager (at most 100 widgets): in a lazy stack, touching and holding a widget's check logged it instead of opening the widget's menu. Drawing widgets only once they scrolled into view was tried and not kept: widgets off screen then had no content for accessibility queries, so a UI test couldn't find a widget just added below the fold. `DashboardGrid`, a custom layout, places the widgets from one flat list (each reads its size from a container value), so a widget keeps its identity and slides when the order changes. Dragging a widget uses system drag and drop: the tile's `contextMenu` comes before its `onDrag`, which lets iOS hand a hold that opened the menu over to a drag once the finger moves (with the order reversed, the menu opened and the widget never lifted). The page's drop delegate reorders a local copy of the order as the finger moves, waiting 12 points after each move so a widget that slides under a resting finger doesn't swap straight back, and saves it once on drop, leaving hidden widgets in their places. While a widget is lifted the dashboard tells the overview, which fades the bottom switcher and stops it taking touches: it otherwise took the drag, so widgets beneath it couldn't be reached. iOS reports the drag leaving and re-entering the page when the switcher fades, and a drag held at the bottom scrolls until the finger is below the last widget, so leaving the page doesn't put the widgets back; if the drag stays away for 0.3 s, the order shown is saved. The drag carries a private type visible only to this app, so text dragged in from another app moves nothing. iOS 27's `reorderable()` was tried first: inside the custom layout it dropped each widget's size, so every widget was laid out small, and dragging didn't reorder. Habit cards drag the same way: their menus stay on the name, check, grid and chips (in the lazy list a menu around a button let a hold run the button), and the overview puts one `onDrag` around the whole card, outside them, which hands over as well. Each card is a drop target; entering one moves the dragged card into its place, and the card it just swapped with is passed over until another card is entered, so a taller card that slides back under a resting finger doesn't swap straight back. `BuddyData.reorder` saves the order shown, leaving habits in other categories and hidden habits in their places. Image exports measure the layout first and lower the scale so no image needs more than 24 million pixels; Year Review shares 12 habits (24 in Grid) per image; encoding and writing run in the background, and a second tap while rendering does nothing.
